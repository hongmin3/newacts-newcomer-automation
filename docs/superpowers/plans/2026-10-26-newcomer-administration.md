# 새가족 교적 등록·주보 작성 자동화 상세 구현 계획

> 실행 담당자: 이 문서는 계획이다. 제품 코드를 구현하거나 운영 자료를 변경하지 않았다. 구현을 시작할 때 `executing-plans` 스킬로 작업별 검증을 수행한다. 병렬 작업은 실행 방법이 별도로 정해졌을 때만 사용한다.

**목표:** 담당자가 등록 대상과 변경 내용을 확인하면, 새가족 등록 명단·디모데 교적·다음 주 주보·전도자 집계를 차례로 반영하고 중단된 단계부터 안전하게 이어간다.

**방식:** 사용자가 2026-10-26에 선택한 **담당자 확인 후 반영**을 따른다. 조회·대조·초안 작성과 외부 저장을 분리한다. 미해결 항목은 이유를 보여 주고, 확인된 사람만 다음 단계로 넘긴다.

**테스트 제한:** 사용자가 확정한 대로 **테스트 중 운영 디모데에 신규 등록·수정·삭제를 하지 않는다.** 실제 사람을 대상으로 한 소수 저장 시험도 하지 않는다. 운영 연결은 읽기 전용으로 한정하고 저장·실패·복구는 모의 페이지 또는 제공자가 분리한 시험 서버에서 검증한다. 주보는 테스트용 사본을 만들어 편집·저장·재열기까지 시험할 수 있다.

**실행 환경:** 사용자가 2026-10-26에 확정한 **Windows 전용**이다. 수집·검토·디모데·한글 편집·공유 저장을 지정 Windows PC에서 수행한다. Mac 앱 개발·연동·패키징은 이번 기능 범위에 넣지 않는다.

**구성 제안:** 현재 저장소 안에 `newcomer-administration/` Python 실행 모듈을 추가한다. 기존 Python의 인증·검색 구조를 참고하되 교적 등록·주보 편집 전용 경계를 둔다. Windows 한글의 자동화 인터페이스를 실제 주보 사본으로 시험한 뒤 사용한다. 한글 버전·설치 구성·공유 폴더 권한은 아직 확인하지 않았다.

**기술 제안:** 기존 Python·Playwright·Google API·SQLite를 우선 사용한다. 한글 연동 의존성은 실제 주보 사본으로 호환성을 확인한 뒤 최소한으로 추가한다. OCR·생성형 AI는 첫 구현의 필수 요소로 두지 않는다.

**사양 근거:** 현재 [SPEC.md](../../../SPEC.md)의 REQ-REG-001~004, REQ-VISITOR-001~004, NFR-SEC-001·NFR-OPS-001·NFR-DATA-001·NFR-SYNC-001, [행축 당일 명단 사양](../../../specs/event-day-workbook.md)의 REQ-EVENTDAYWORKBOOK-001~005.

**업무 원문:** Google Docs 「교적 등록 및 주보 등록 방법」. 본문과 포함된 화면 이미지 10개를 확인했다. 원문 계정·암호·개인 명단·공유 서버 주소는 이 문서에 옮기지 않았다. 원문은 변경하지 않았다.

**기준 판:** 원격 `main`의 `6614053`을 pull한 뒤 조사했다. 기존 로컬 검사기·지침 변경은 별도 보존했다. 이 계획에서 제안하는 신규 동작은 아직 승인된 제품 사양이 아니다. 구현 전에 기능 사양을 등록하고 미확정 정책을 확정해야 한다.

## 1. 읽는 순서와 완료 범위

운영 담당자는 2~5절에서 업무 범위와 확인 항목을 읽고, 8~10절에서 예외·복구·도입 절차를 확인한다. 구현 담당자는 공통 규칙과 인터페이스를 읽은 뒤 11절 작업을 순서대로 수행한다.

계획 작성의 완료 조건은 원문 업무 누락 여부, 기존 구현 재사용, 미확정 정책, 오류 후 복구, 테스트와 운영 확인 절차가 연결되는 것이다. 모든 운영 예외를 이미 확인했다고 주장하지 않는다. 실제 교적 화면·한글 원본·공유 폴더로만 확인할 수 있는 조건은 별도로 표시한다.

제품 구현의 완료 조건은 다음과 같다.

1. 미리보기에서 등록·방문·기등록·검토 필요를 구분하고 외부 쓰기는 0회다.
2. 담당자가 승인한 사람과 필드만 외부 시스템에 저장한다.
3. 같은 작업을 다시 실행해도 교적·주보 번호·전도 실적이 중복되지 않는다.
4. 실패한 단계와 결과가 불확실한 단계를 구분하고, 이미 끝난 단계는 보존한다.
5. 주보를 다시 열어 본문·전도자 집계·색상·합계를 확인한다.
6. 교적 저장·시트 반영은 모의 교적과 시험용 시트에서, 한글은 테스트 사본에서 확인한다. 운영 디모데는 읽기 전용 연결만 확인한다. 별도 시험 서버가 없으면 실제 서버의 저장 동작은 미검증으로 남긴다.

## 2. 원문 업무와 자동화 범위

| 원문 업무 | 현재 확인한 상태 | 이번 계획의 처리 |
|---|---|---|
| 등록카드 내용을 해당 날짜의 등록 명단에 입력 | 카드 입력 전용 자동화는 이번 조사에서 확인하지 않음 | 1차는 입력된 시트를 기준으로 검증. 카드 사진 입력은 후속 선택 기능 |
| 등록 새가족 군 현황 정리 | REQ-REG-002~004에 기존 구현 있음 | 기존 생성기를 유지하고 검증 결과만 연결 |
| 행축 방문자 명단 정리 | 하반기 방문 관리와 별도 행사 당일 명단 구현 있음 | 입력 경로를 구분. 순수 방문자는 교적·주보에 보내지 않음 |
| 교적의 동명이인 확인 | 정착률 코드에 조회용 후보 검색 구현 있음 | 신규 등록용 동일인 판정과 영문 구분자 보존 규칙을 별도 구현 |
| 이미 등록된 사람은 기등록 표시 | 신규 교적 작성 후 되쓰기 기능은 확인하지 않음 | 기존 교적이 확인되면 새 교적을 만들지 않고 승인 후 기등록 표시 |
| 이름·성별·생년월일·주소·전화·인도자·소속 입력 | 교적 신규 생성 구현은 조사 범위에서 확인하지 않음 | 전용 입력·저장·재조회 절차 추가 |
| 다음 주 한글 주보 준비 | 저장소의 해당 편집기 구현은 확인하지 않음 | 날짜 선택·사본 생성·두 영역 편집·검증·최종 저장 단계 추가 |
| 환영 명단에 등록자만 기재 | 원문 화면에 번호·이름·교구·인도자 예시 있음 | 승인된 명단으로 생성. 교구 표기는 `청년` |
| 전도자 누적 현황 이동·신규 추가·빨간색 | 한글 표의 누적 인원별 칸에 이름이 배치됨 | 이름·누적 실적 모델에서 결과를 계산하고 표에 반영 |
| 교역자는 전도자 실적 집계에서 제외 | 제외 기준은 원문 예시만 있음 | 담당자가 확인한 교역자 식별 목록 사용. 개인 이름을 코드에 고정하지 않음 |
| 총계와 마지막 새가족 번호 비교 | 원문에 대조 규칙 있음 | 기존 기준 합계부터 확인하고 예외는 마감 차단 |
| 등록·방문 실물 카드 전달 | 물리 작업 | 인계 목록·완료 확인만 제공. 자동 전달로 표시하지 않음 |

### 2.1 전체 처리 흐름

```flow
담당자 날짜·대상 시트 선택 -> 명단 읽기·필수값 검사 -> 방문·등록·중복 분류
방문·등록·중복 분류 -> 교적 후보 조회 -> 담당자 대상·예외 확인
담당자 대상·예외 확인 -> 승인된 교적 저장·재조회 -> 시트 필요한 값 반영·재조회
시트 필요한 값 반영·재조회 -> 다음 주 주보 사본 작성 -> 명단·전도자·합계 검증
명단·전도자·합계 검증 -> 담당자 최종 확인 -> 공유 폴더 저장·다시 읽기
교적 저장·재조회 -(결과 불명)-> 재조회 대기
공유 폴더 저장·다시 읽기 -(실패)-> 초안 보존·저장 단계 재개
```

### 2.2 기본안과 다른 선택지

| 선택지 | 장점 | 비용·제약 | 판단 |
|---|---|---|---|
| 담당자 확인 후 단계별 반영 | 이름·소속·주보 날짜를 반영 전에 확인하고 오류 범위를 줄임 | 확인 작업 필요 | 사용자 선택. 기본 구현 |
| Sheets 검증과 복사할 명단까지만 생성 | 가장 빨리 제공 가능하며 한글 환경 의존성이 작음 | 교적·주보의 반복 입력이 남음 | 한글 연동이 막힐 때 부분 제공 경로 |
| 무인 예약 실행 | 확인 없이 반복 작업 수행 | 화면 변화·교역자 목록·문서 잠금·저장 불명 처리의 운영 검증이 선행되어야 함 | 1차 제외. 별도 승인 후 검토 |

## 3. 공통 규칙

- 기존 `active`, `mode`, 수신자, 시트 ID·이름·열 위치, Apps Script 실행 함수명은 바꾸지 않는다.
- 기존 교육·수료·정착률 작업과 새 작업의 상태 저장소·잠금·처리 완료 표시를 분리한다.
- 새 기능은 Windows PowerShell 실행·Windows 사용자 인증 저장·NTFS 접근 권한·Windows 파일 잠금을 기준으로 구현한다. `fcntl`, POSIX 파일 권한 검사, `.venv/bin/python`, macOS 키체인에 의존하지 않는다.
- `run*Test`라는 이름은 무변경 실행의 근거가 아니다. 모든 외부 쓰기 호출을 차단한 미리보기 경계를 시험한다.
- 등록 유지관리의 기존 이름 보정 금지(REQ-REG-001)는 유지한다. 교적명 되쓰기는 별도 승인한 신규 기능에서만 수행한다.
- 이름 끝 영문 구분자는 표시·저장·동일인 판정에서 보존한다. 검색 후보를 넓히는 값과 저장할 이름을 구분한다.
- 전화번호의 앞자리 0과 생년월일을 보존한다. 입력이 나이뿐이면 정확한 생년월일을 만들어 내지 않는다.
- 등록 명단 A열 번호, 영구 관리 식별자, 주보 누적 번호는 서로 다른 값이다.
- 명단 추가 후 날짜 오름차순·같은 날짜 기존 순서·A열 재번호·날짜별 흰색/연한 파란색 정리를 따른다. 머리글·오른쪽 집계·수식·선택 목록·중복 경고는 보존한다.
- 기준 시간대는 `Asia/Seoul`로 제안한다. 대상 등록 기간과 주보 발행일은 화면에 각각 표시하고 담당자가 확정한다.
- 개인 명단·카드·교적 후보·한글 원본·실행 이력·인증 정보는 저장소 밖 접근이 제한된 경로에 둔다. 테스트에는 합성 자료만 쓴다.
- 전도 실적은 성공한 신규 교적 수와 같은 값이라고 가정하지 않는다. 승인된 주보·실적 대상 집합을 별도로 계산한다.
- 예약 실행·운영 메일·기존 Apps Script 배포는 이번 계획에 포함하지 않는다. 등록 자동화 전체 함수를 호출하면 메일·방문 반영까지 일어날 수 있으므로 단순 현황 갱신과 구분한다.
- 테스트 실행은 운영 디모데 writer를 만들 수 없게 구성한다. 버튼을 안 누르겠다는 규칙에만 의존하지 않고, 테스트 경계에서 운영 주소로 향하는 저장 요청을 차단한다. ‘만들었다가 삭제’·실제 처리 대상의 소수 저장도 테스트 방법으로 쓰지 않는다.

워크스페이스의 프로젝트 목록에서 디모데 수료 입력 프로젝트를 찾았다. `projects/`의 Python·JavaScript·Markdown을 `HwpObject`, `HWPFrame`, `hwpapi`, `hwpx`, `pyhwpx`로 검색한 범위에서는 주보 편집 재사용 모듈을 찾지 못했다. 제외 파일·접근하지 않은 저장소까지 구현이 없다는 뜻은 아니다.

### 4.1 사양·요청 간 충돌과 처리

```text
SPEC / CODE MISMATCH

Requirement: REQ-VISITOR-001과 프로젝트 명단 입력 지침의 나이 기준
Specification: 기존 방문 자동 반영 사양은 등록일 기준 만 나이를 사용한다.
Current Implementation: 기존 방문 동기화는 생년월일로 나이를 계산하며, 최신 AGENTS.md는 출생연도 입력 시 세는나이를 요구한다.
Difference: 원본 열에 나이와 생년월일이 혼재할 때 서로 다른 나이 값을 만들 수 있다. 기존 구현의 실제 모든 입력별 결과는 이번 계획에서 재실행하지 않았다.
Action: 사용자 확인 필요. 기존 사양·코드는 이번 작업에서 변경하지 않는다. 승인 후 범위를 정해 해당 사양과 테스트를 먼저 정리한다.
```

새 기능의 출생연도 입력은 최신 사용자 지침인 `기준 연도 - 출생연도 + 1`을 따른다. 단, 이 값으로 생일의 월·일을 추정하거나 기존 만 나이 열을 일괄 변경하지 않는다.

원문의 ‘교적 확정 이름을 시트에도 반영’은 REQ-REG-001의 교육 응답 기반 이름 자동 보정 금지와 목적이 다르다. 기존 보정기의 이름 수정 범위를 넓히지 않고, 새 기능에서 해당 사람·필드에 대한 승인 기록을 남겨 적용한다.

## 6. 데이터와 공통 인터페이스 제안

아래 계약은 구현 시작 시 사양과 함께 확정한다. 선택하지 않은 입력은 비워 두고, 필수 여부는 작업 단계별 검증으로 판단한다. 개인정보를 담는 실제 JSON·DB는 Git 밖에 둔다.

### Contract: SourceRef

| 필드 | 형식 | 의미 |
|---|---|---|
| `source_kind` | `registration_sheet` 또는 `event_workbook` | 원본 종류 |
| `source_config_key` | 문자열 | 로컬 설정의 대상 참조 키. 실제 파일 ID는 설정 밖 보고서에 쓰지 않음 |
| `record_id` | 문자열 | 영구 식별자. A열 번호·행 번호·이름이 바뀌어도 유지 |
| `observed_row` | 정수 | 조회 당시 행. 쓰기 주소의 유일한 근거로 사용 금지 |
| `source_version` | SHA-256 문자열 | 자동화가 쓰는 대상 필드·형식의 조회 판 |

행사 명단에 기존 관리번호가 있으면 source 종류와 묶어 사용한다. 일반 시트에는 새 열을 임의로 넣지 않는다. 승인된 관리 식별자 열 또는 행에 붙는 메타데이터를 조사하고, 정렬 후 추적이 입증된 방식을 선택한다. 로컬 전화번호 해시만으로 사람의 영구 식별자를 만드는 안은 제외한다.

### Contract: Applicant

| `source` | SourceRef | 원본 식별과 판 |
| `entry_kind` | `visitor` / `registration` | 방문 전용과 등록 의도 구분 |
| `registration_date` | ISO 날짜 또는 null | 입력 기준일 |

| `birth_year`, `age` | 정수 또는 null | 출생연도·표시 나이. 생년월일과 구분 |

| `previous_registration_mark` | 문자열 또는 null | 기존 기등록 셀 값. 작업 완료 플래그와 혼용 금지 |

### Contract: IdentityDecision

| 필드 | 형식 | 의미 |
|---|---|---|
| `record_id` | 문자열 | 대상 |
| `decision` | `CREATE` / `EXISTING` / `REVIEW` / `VISITOR_ONLY` | 신규·기등록·보류·방문 |
| `candidate_ids` | 문자열 배열 | 교적 조회에서 확인된 후보 식별자 |
| `confirmed_person_id` | 문자열 또는 null | 한 사람으로 확정했을 때만 저장 |
| `canonical_name` | 문자열 또는 null | 교적의 영문 구분자를 포함한 이름 |
| `reason_codes` | 문자열 배열 | `PHONE_SHARED`, `DOB_CONFLICT`, `SEARCH_INCOMPLETE` 등 |
| `evidence_version` | 문자열 | 조회 결과 판. 전체 개인정보 본문을 중복 저장하지 않음 |
| `confirmed_by`, `confirmed_at` | 로컬 사용자 참조, ISO 시각 또는 null | 담당자 판정 기록 |

`CREATE`는 이름 검색 0건만으로 확정하지 않는다. 검색 완료·범위·이름 변형·전화·생년월일 대조와 담당자 확인을 모두 거친다. 가족 공용 번호는 동일인의 충분조건이 아니다.

### Contract: ApprovedBatch

`batch_id: str`, `source_period_start: date`, `source_period_end: date`, `bulletin_date: date`, `template_hash: str`, `policy_version: str`, `records: list[ApprovedRecord]`, `approved_at: datetime`, `approval_digest: str`를 가진다.

`ApprovedRecord`는 `record_id`, `source_version`, `identity_decision`, `allowed_field_changes: dict[str, {before, after}]`, `include_in_bulletin: bool`, `include_in_total: bool`, `introducer_credit: list[{introducer_id, units: int}]`, `canonical_name`, `organization_ids`를 가진다. `units` 허용값과 공동 인도자 규칙은 D05 확정 전 사용할 수 없다.

승인 뒤 원본·후보 판정·양식·정책·날짜 가운데 하나가 바뀌면 해당 승인 digest를 폐기한다. 한 명 승인과 전체 일괄 승인은 별도 범위로 기록한다.

### Contract: StepResult와 OperationStore

`StepResult` 필드: `batch_id: str`, `record_id: str|null`, `step: str`, `attempt: int`, `state: str`, `external_id: str|null`, `before_digest: str|null`, `after_digest: str|null`, `reason_code: str|null`, `verified_at: datetime|null`.

상태는 `PENDING`, `READY`, `REVIEW`, `APPLYING`, `VERIFIED`, `FAILED`, `UNKNOWN`, `SKIPPED`로 제한한다. `UNKNOWN`은 요청이 전달되었을 수 있어 재조회 전 같은 쓰기를 반복하지 않는 상태다. `SKIPPED`에는 방문 전용 등 사유가 있어야 하며 성공 인원에 합치지 않는다.

저장소 인터페이스: `begin_step(batch_id, record_id, step, before_digest) -> Attempt`, `finish_step(attempt_id, state, external_id=None, after_digest=None) -> None`, `load_pending(batch_id) -> list[StepResult]`. 외부 요청 전에 시도 상태를 저장하고 결과 확인 후 갱신한다. 로컬 DB 트랜잭션은 외부 교적·Sheets·한글 파일까지 한 번에 취소하지 못한다.

`Attempt` 필드는 `attempt_id: str`, `batch_id: str`, `record_id: str|null`, `step: str`, `attempt: int`, `started_at: datetime`, `before_digest: str|null`이다. 자동화가 임의로 외부 교적 ID를 만들어 넣지 않는다.

### Contract: BulletinBaseline

`file_path: str`, `file_hash: str`, `publication_date: date`, `last_number: int`, `total: int`, `section_totals: dict[str,int]`, `introducers: list[{introducer_id: str, display_name: str, count: int, location: str}]`, `template_profile_version: str`, `issues: list[str]`를 가진다. `location`은 확인된 표/문단 위치의 adapter 내부 참조다. 기준값이 중복되거나 모순되면 `issues`를 비우지 않고 계획 생성을 차단한다.

### Contract: BulletinPlan

`bulletin_date: date`, `source_batch_ids: list[str]`, `baseline_file_hash: str`, `template_profile_version: str`, `baseline_last_number: int`, `baseline_total: int`, `entries: list[{record_id, number, name, parish, introducer}]`, `introducer_changes: list[{introducer_id, old_count, delta, new_count, highlight}]`, `section_totals: dict[str,int]`, `expected_last_number: int`, `expected_total: int`, `draft_path: str`, `validation_issues: list[str]`를 가진다.

`parish`는 원문 기준 `청년`이다. `number`는 기준 누적번호 다음 값부터 예약하되, 초안 취소 시 운영 번호가 소비됐다고 기록하지 않는다. 이미 게시된 번호는 후속 등록 취소 때 자동 재번호하지 않고 정정 절차로 넘긴다.

### Contract: 외부 경계 함수

```python
read_applicants(source_config, period) -> list[Applicant]
inspect_identity(applicant, dimode_reader) -> IdentityDecision
build_approved_batch(applicants, decisions, approvals, policy) -> ApprovedBatch
apply_dimode_registration(record, dimode_writer, operation_store) -> StepResult
apply_source_patch(record, sheets_writer, operation_store) -> StepResult
build_bulletin_plan(batch, baseline, policy, operation_store) -> BulletinPlan
write_bulletin_draft(plan, hwp_adapter, operation_store) -> StepResult
verify_bulletin(plan, hwp_adapter) -> ValidationReport
publish_bulletin(plan, expected_target_hash, file_adapter, operation_store) -> StepResult
```

`ValidationReport`는 `passed: bool`, `checks: list[{code, expected, actual, passed}]`, `review_files: list[str]`를 가진다. 모든 adapter는 읽기/쓰기를 분리하며 미리보기에는 writer 객체를 전달하지 않는다.

### Contract: TestNetworkPolicy

`classify_test_request(request: RequestDescriptor, mode: TestMode, rules: list[ReadRule]) -> Literal['ALLOW_READ', 'MOCK', 'BLOCK']`를 제공한다. `TestMode`는 10.3절의 세 모드다.

`RequestDescriptor` 필드: `origin: str`, `path: str`, `method: str`, `resource_type: str`, `event_target: str|null`, `submit_control: str|null`, `query_action: str|null`, `has_unknown_action: bool`. 실제 폼 본문을 분석하더라도 인증·개인값을 이 계약의 로그에 넣지 않는다.

`ReadRule`은 `origin: str`, `path: str`, `method: str`, `operation: Literal['LOGIN','SEARCH','VIEW','STATIC']`, `event_target: str|null`, `submit_control: str|null`, `allowed_query_keys: list[str]`를 가진다. 모든 조건이 맞는 확인된 규칙만 허용하며 미등록 이벤트·저장/삭제 동작은 `BLOCK`이다. `OFFLINE_SIMULATED`에서 외부 주소는 언제나 `BLOCK`, 합성 주소는 `MOCK`이다. classifier와 브라우저 통신 기록을 각각 검증한다.

## 7. 단계별 업무 설계

### 7.1 명단 수집·정리

1. 담당자가 원본 종류·등록 기간·주보 발행일을 선택한다. ‘최근 파일’이나 현재 PC 날짜만으로 주보 대상을 정하지 않는다.
2. 실제 머리글·전체 관리 열·수식·입력 선택 규칙을 읽는다. 같은 이름 머리글, 없는 필수 열, 예상과 다른 양식은 중단한다.
3. 입력 원본을 `Applicant`로 변환하고 필드별 오류를 표시한다. 빈 행·합계 행·방문 전용·행사 취소 기록은 등록 목록에서 제외하되 제외 사유와 건수를 남긴다.
4. 같은 사람으로 의심되는 자료는 후보로 묶어 보여 주며 이름이나 전화만으로 자동 합치지 않는다.
5. 일반 등록과 행사 명단을 연결하기로 결정하면 원본 관리번호 사이의 연결을 저장한다. 각각 한 사람을 두 번 처리하지 않는 시험을 추가한다.
6. 명단을 실제 추가·정리할 때는 허용 범위의 모든 열을 함께 이동한다. A열 번호는 다시 매기되 교적 처리 상태·주보 번호는 따라붙는 식별자로 추적한다.

### 7.2 교적 후보 확인

1. 기존 인증 경로로 로그인한다. 문서에 있는 계정·암호를 코드나 설정 예시에 복사하지 않는다.
2. 현재 계정이 의도한 교회·청년 조직·연도에 들어왔는지 확인한다. 로그인 성공과 등록 권한 보유를 구분한다.
3. 전화번호와 이름을 각각 조회하고, 후보의 정확한 생년월일·연락처·이름·식별자를 대조한다. 검색 결과가 여러 페이지면 끝까지 읽었는지 확인한다.
4. 같은 사람으로 확인되면 `EXISTING`으로 두고 새 교적을 생성하지 않는다. 이름·전화·생일 중 충돌이 있거나 후보를 다 읽지 못했으면 `REVIEW`다.
5. 동명이인이 서로 다른 사람으로 확인되면 사이트가 사용하는 영문 구분자 생성·충돌 검사 방식에 맞춰 이름을 제안한다. `A`부터 임의로 배정하지 않는다.
6. 군→팀→순 선택은 표시 문자열과 실제 조직 ID를 함께 확인한다. 순을 모르는 경우 원문 규칙대로 팀장순을 후보로 제안하되, 목록 맨 위가 팀장인지 확인한 뒤 담당자가 선택한다.

### 7.3 승인과 교적 저장

승인 화면은 사람별 ‘원본 / 교적 후보 / 적용 값 / 보류 이유’를 보여 준다. 전체 승인 전에 신규 생성·기등록 표시·교적명 변경·주보 포함·실적 포함 건수를 각각 표시한다.

승인 직전 원본과 후보를 다시 읽는다. 변경되었으면 해당 사람 승인을 취소한다. 저장 직전에도 신규 생성 후보가 아직 없는지 다시 조회한다.

교적 신규 입력은 원문 필드인 이름·구분자·성별·신앙세대 관계 `본인`·생년월일·주소·휴대전화·인도자·조직연도·군·팀·순·교인구분 `청년/새가족`을 사용한다. 화면에 추가 필수값이 있으면 문서에서 추정하지 않고 별도 사양으로 확정한다. 선택하지 않은 문자 수신·가족 관계 등 부가 옵션을 일괄 변경하지 않는다.

저장은 한 번 요청한 뒤 생성된 교적 ID와 필드 값을 재조회한다. 버튼 클릭·팝업 닫힘·HTTP 200만으로 성공 처리하지 않는다. 실패인지 성공인지 모르면 `UNKNOWN`으로 두고 조회로 먼저 해소한다.

### 7.4 시트 반영

- 기등록 확인자: 승인된 기등록 셀만 수정한다. 기존에 기등록인 사람과 이번 실행에서 새 교적을 만든 사람의 처리 완료 상태를 구분한다.
- 새 교적 확인자: 교적 ID·완료 정보는 승인된 관리 저장소에 남긴다. 기등록 칸에 무조건 `O`를 적어 뜻을 바꾸지 않는다.
- 교적명: 담당자가 승인한 최종 이름만 반영한다. 교육 명단·행사 원본까지 일괄 이름 변경하지 않는다. 다른 이름 소비자에 미치는 영향은 검토 대상으로 표시한다.
- 쓰기 전 행을 식별자로 다시 찾고 원본 판을 대조한다. 행 이동·이름 변경을 감지하면 범위를 다시 계산한다.
- 한 묶음의 시트 변경은 가능한 한 `spreadsheets.batchUpdate`로 처리한다. 이는 해당 요청 내부 변경에만 적용되며 교적 저장·다른 파일과의 공동 취소를 뜻하지 않는다.
- Google Sheets 공동 편집의 읽기→쓰기 사이 경쟁은 남는다. 운영 쓰기 구간의 편집 조정과 쓰기 후 재조회가 필요하며, 단순 사전 해시 비교를 원자적 비교 후 저장이라고 부르지 않는다.
- 서식 정리와 정렬이 기존 Apps Script의 행 참조·보정 상태를 흐트러뜨리지 않는지 재실행한다. 이름·전화 수정 후 방문 동기화가 새 사람을 추가하지 않는지 확인한다.

### 7.5 주보와 전도자 계산

1. 주보용 기준은 승인한 명단의 확정 이름이다. 순수 방문자·미해결 교적 결과·정책 미정 기등록자는 기본 주보 반영을 보류한다.
2. 기준 주보에서 마지막 사용 번호와 전체 합계, 청년 합계, 전도자별 누적 실적을 읽는다. 이름만 있는 문장 목록을 쉼표로 단순 분해하지 않고 표·문단 구조를 확인한다.
3. 새가족 번호는 `기준 마지막 번호 + 1`부터 승인된 등록 순서대로 부여한다. 입력 시트의 A열 번호는 쓰지 않는다.
4. 같은 인도자의 이번 대상 인원을 먼저 합산한다. 예를 들어 가상 인도자A의 기존 실적이 9이고 대상이 2이면 11명 칸으로 한 번 이동한다.
5. 새 인도자가 2명을 인도했다면 2명 칸에 한 번 넣는다. 사람마다 1명 칸에 덧붙이는 방식으로 중복 생성하지 않는다.
6. 교역자·스스로·미확정 인도자는 각 정책으로 분기한다. 교역자의 실적 제외가 새가족 명단·청년 총계 제외를 뜻한다고 추정하지 않는다.
7. 전도 실적표에서 기존 위치의 이름을 제거하고 새 위치에 한 번만 기록한다. 동일한 실적 칸 안의 다른 이름·구분자·서식은 보존한다.
8. 이번 작업에서 이동·신규 추가된 이름만 빨간색 대상으로 계산한다. 지난 주 빨간색 처리 범위는 D11 확정 후 적용한다.
9. 이번 청년 추가 인원·전체 총계·마지막 번호를 대조한다. 기존 다른 교구 값과 계산식은 보존한다.

대조식은 정책별로 분리한다.

- `새 마지막 번호 = 기준 마지막 번호 + 이번 번호 부여 대상 수`
- `새 청년 총계 = 기준 청년 총계 + 이번 총계 반영 대상 수`
- `인도자 새 실적 = 기준 실적 + 이번 승인 실적 - 승인된 정정 실적`
- `주보 총계 = 교구별 총계의 합`은 해당 양식이 이 구조임을 확인한 경우 적용한다.
- `마지막 번호 = 총계`는 원문에서 요구하므로 기준 시점부터 확인한다. 번호 초기화·번호 공백·다른 교구 포함으로 성립하지 않으면 자동 보정하지 않고 마감을 보류한다.

전도자 실적 합계는 교역자 제외 등으로 전체 새가족 수와 다를 수 있다. 두 수를 같게 맞추려고 가상 인도자나 실적을 만들지 않는다.

### 7.6 한글 파일 편집·최종 저장

원문 화면에는 ‘환영합니다’ 명단과 ‘전도자 현황’이 보이지만, 실제 한글 파일의 책갈피·누름틀·표·별도 쪽 여부는 확인하지 않았다. Excel 시트 API처럼 취급하지 않고 실제 파일 사본에서 위치를 조사한다.

1. 발행일에 해당하는 폴더와 한글 파일을 찾고, 선택한 경로·문서 내부 날짜·발행일을 대조한다. Excel 파일은 편집하지 않는다.
2. 다음 주 파일이 있으면 그 파일을 기준으로 한다. 여러 파일이 있으면 담당자가 고른다. 없으면 확정한 이번 주 한글 파일을 새 작업 사본으로 복사한다.
3. ‘파일명 날짜 변경’과 ‘본문 주보 전체 날짜 변경’을 구분한다. 환영/전도자 범위 밖 예배순서·설교·광고를 자동으로 다음 주 내용으로 바꾸지 않는다.
4. 편집 전 원본 해시와 수정 시각을 기록하고 작업용 사본에서만 두 영역을 편집한다. 기존 한글 문서·사용자가 띄운 한글 프로세스를 종료하지 않는다.
5. 표 행 증가, 셀 병합, 글자색, 줄바꿈을 처리하고 같은 실적 내 이름들이 잘리지 않는지 렌더링으로 확인한다.
6. 저장 후 다시 열어 번호·이름·교구·인도자·집계·날짜를 읽는다. 미리보기 또는 PDF로 페이지 밀림과 글자 누락을 확인한다. PDF는 검토용이며 한글 최종본을 대체하지 않는다.
7. 담당자가 초안을 승인하면 공유 대상이 처음 읽은 판과 같은지 다시 확인한다. 다른 사람이 바꿨으면 덮어쓰지 않고 비교한다.
8. 같은 공유 폴더에 임시 이름으로 복사하고 열기·해시를 확인한 뒤 최종 이름으로 확정한다. SMB 서버의 rename·잠금 동작은 실제 환경에서 시험한다. 네트워크 전체에 원자성을 보장한다고 가정하지 않는다.
9. 최종 경로에서 다시 읽고 파일 해시·명단 수·마지막 번호를 확인한다. 작업 사본 성공과 최종 저장 성공을 별개로 기록한다.

| 한글 소유 범위 | 자동화가 만든 인스턴스·작업 사본만 제어 | 기존 사용자의 문서·프로세스를 연결하거나 닫지 않는지 확인 |
| 보안 대화상자 | 승인한 공식 보안모듈 설치·등록 절차만 문서화 | 보안 설정 전체 해제·임의 DLL 설치·레지스트리 일괄 변경 금지 |
| 공유 폴더 | 로컬 설정에 UNC 경로 저장. 드라이브 문자 매핑에만 의존하지 않음 | 한국어·공백·긴 파일명, SMB 잠금·끊김·용량 부족 확인 |
| 화면 세션 | 최초 운영은 담당자가 사용하는 대화형 Windows 세션 | 잠금·로그오프·절전·RDP 재접속 중 한글 동작은 실제 검증. 화면 없이 동작한다고 가정하지 않음 |

기본 UI는 검토 목록·사람별 변경 승인·주보 최종 승인을 구분하는 수동 실행기다. GUI 형태가 필요하면 Windows용 화면을 이 경계 위에 붙인다. 기존 Mac Qt 앱을 이 기능의 필수 실행기로 사용하지 않는다.

## 8. 예외 처리표

‘개별 보류’는 해당 사람의 후속 작업을 막고 다른 승인 대상은 계속할 수 있다는 뜻이다. ‘전체 중단’은 대상·권한·양식·기준이 불확실해 새 외부 변경을 멈춘다는 뜻이다. 일부 인원만 주보에 넣는 경우 제외 명단을 표시한 새 승인을 받아야 한다.

## 9. 재실행·취소·정정 설계

### 9.1 단계별 기록

사람별 단계는 `SOURCE_VALIDATED → IDENTITY_CONFIRMED → APPROVED → DIMODE_VERIFIED → SHEET_VERIFIED`다. 기등록은 `DIMODE_EXISTING_VERIFIED`를 사용하며 신규 저장과 구별한다. 방문 전용은 해당 사유로 교적 단계에서 종료한다.

주보별 단계는 `BASELINE_VERIFIED → BULLETIN_PLANNED → DRAFT_WRITTEN → DRAFT_VERIFIED → FINAL_APPROVED → PUBLISHED_VERIFIED`다. 전도자 실적 반영분은 `(record_id, bulletin_date, credit_kind)` 기준으로 한 번만 적용한다.

주보 초안을 다시 만들 때 이전 초안의 누적값에 더하지 않는다. 확정한 기준 파일과 아직 최종 반영되지 않은 승인 내역에서 결과를 다시 계산한다.

### 9.2 실패 시 재개 위치

| 실패 위치 | 보존할 것 | 재개 |
|---|---|---|
| 교적 요청 전 | 승인과 조회 근거 | 변경 여부 재확인 후 해당 사람부터 |
| 교적 저장 결과 불명 | 요청 시각·후보 ID·입력 판 | 교적 재조회로 존재 여부 확인 |
| 교적 완료, 시트 미반영 | 교적 ID·완료 상태 | 시트 필드 반영만 수행 |
| 시트 완료, 초안 실패 | 확정 이름·주보 대상 | 기준 파일로 초안 재생성 |
| 초안 완료, 공유 저장 실패 | 검증된 초안 해시 | 공유 대상 확인 후 저장만 재시도 |
| 공유 저장 결과 불명 | 대상 경로·예상 해시 | 최종 파일 다시 읽어 일치 확인 |

### 9.3 잠금과 다른 작업의 충돌

초기 운영은 한 대의 지정 Windows PC와 Windows 계정에서 한 작성자만 허용하는 안을 제안한다. 동일 PC에서는 Windows 파일 잠금을 사용하고, 정착률 브라우저·한글 실행과 세션을 공유하지 않는다. 프로세스 강제 종료 후 OS가 잠금을 해제하더라도, 이전 `APPLYING` 단계의 외부 결과는 재조회한다.

여러 PC 쓰기가 필요하면 공통 잠금과 만료·소유자·갱신·오래된 실행 차단 검사를 먼저 설계한다. 로컬 SQLite 잠금이나 파일 하나의 존재만으로 다른 PC의 교적 중복 저장을 막았다고 주장하지 않는다. 사용자 편집과 기존 월요일 자동화가 겹치는 시간은 사전 확인하며 기존 실행 일정을 임의 변경하지 않는다.

## 10. 도입 순서와 운영 확인

| 단계 | 제공하는 것 | 외부 영향 | 다음 단계 조건 |
|---|---|---|---|
| 0. 사양·환경 확인 | 정책 답, 실제 양식 구조, 권한 점검 | 읽기만. 운영 조회도 합의 범위에서 | D01~D15의 적용 항목 확정 |
| 1. 명단·교적 대조 미리보기 | 대상·중복·기등록·보류·변경 예정 | 외부 쓰기 0 | 합성 회귀와 승인된 조회 시험 통과 |
| 2. 모의 교적·시험용 시트 | 사람별 승인·저장 후 재조회·복구 | 운영 디모데 쓰기 0. 합성 자료와 별도 시험 시트만 사용 | 신규·기등록·응답 유실·재실행 시험 통과 |

| 4. 저장 절차 검증 | 최종 승인·충돌 검사·다시 읽기 | 로컬 테스트 폴더 또는 지정된 공유 시험 폴더만 변경 | 테스트 결과 파일의 내용·해시 확인 |

운영 디모데에는 테스트용 교인도, 실제 사람의 시험 등록도 하지 않는다. 저장 검증은 모의 페이지 또는 제공자가 운영 데이터와 분리했음을 확인한 시험 서버에서만 한다. 시험 서버가 없으면 실제 서버 저장 성공은 확인하지 못한 상태로 남긴다.

인수 항목은 모의 교적 ID·필드 재조회, 시험 시트의 대상 셀, 이름 소비자 영향, 테스트 주보 명단·색상·표 넘침·저장본이다. 운영 연결에서 확인한 항목과 모의 환경에서 확인한 항목을 나눈다. 메일은 새로 발송하지 않는다. 실물 카드 전달은 자동화 구현을 검증한 것으로 대체하지 않는다.

### 10.1 디모데와 연결하는 테스트를 네 층으로 분리

| 수준 | 연결 대상 | 확인하는 것 | 확인하지 못하는 것 |
|---|---|---|---|
| L1. 합성 업무 시험 | 로컬 합성 명단·SQLite | 동일인 분기, 영문 구분자, 승인, 번호·실적 계산, 재개 | 실제 디모데 UI·서버 제약 |
| L2. 모의 브라우저 연동 | 합성 HTML·프레임·선택 목록·모의 저장 응답 | 실제 Playwright 입력·버튼·팝업·폼 제출·저장 후 재조회와 오류 복구 | 실제 서버가 그 저장을 받아들이는지 |
| L3. 운영 읽기 전용 연결 | 실제 디모데 로그인·검색·조회 화면 | 로그인·권한·프레임·현재 필드·목록 구조·조회 결과 파싱 | 신규 교적 저장·실서버 이름 구분자 할당·서버 저장 검증 |
| L4. 제공자 분리 시험 서버 | 운영 DB와 분리된 것이 확인된 제공자 환경 | 실제 서버 구현의 저장·필수값·중복 규칙 | 운영 환경과 설정이 다르면 그 차이 |

L4는 존재와 분리 여부를 확인하기 전까지 계획상의 선택지다. 임의의 테스트 URL·계정을 만들거나 운영 조직 아래 시험 교구를 만들어 대체하지 않는다.

### 10.2 운영 읽기 전용 연결의 절차

1. 가능하면 디모데 제공자에게 쓰기 권한이 없는 조회 계정을 요청한다. 계정 제공·권한 구조는 아직 확인하지 않았다. 코드 차단과 서버 권한을 함께 쓰는 안이다.
2. 새 브라우저 context에 통신 정책을 먼저 적용하고 페이지를 연다. 기존 로그인 브라우저의 쿠키·개인 세션을 자동으로 가져오지 않는다.
3. 로그인과 승인된 조회 요청만 허용한다. 실제 비밀은 담당자가 입력하거나 승인된 로컬 비밀 저장소를 통해 전달한다. 아이디·암호·세션·`__VIEWSTATE` 원문을 진단 로그에 남기지 않는다.
4. 이름·전화 검색은 먼저 해당 요청의 동작과 이벤트를 확인한 뒤 허용 목록에 등록한다. ASP.NET에서는 조회와 저장이 같은 URL의 POST일 수 있으므로 메서드·경로만으로 허용하지 않는다.
5. 요청의 경로·메서드·조회 이벤트 종류·폼의 제출 버튼을 함께 검사한다. `__EVENTTARGET`, image 버튼의 `.x/.y`, 실제 form action 등 사용하는 방식을 조사한다. 미확인 이벤트는 통과시키지 않는다.
6. 등록 화면은 열람할 수 있는 경우에만 비어 있는 필드·선택 목록 구조를 읽는다. 운영 등록 폼에 테스트 이름·전화·생일을 채우거나 저장 버튼을 눌러 차단 여부를 시험하지 않는다.
7. 브라우저 context 전체의 팝업·하위 프레임에 같은 정책을 적용한다. Service Worker는 차단하고 직접 HTTP client·별도 APIRequestContext·WebSocket 등 우회 통신을 테스트 실행기에서 금지하거나 별도 차단한다.
8. 리다이렉트의 최종 목적지도 검사한다. 요청 차단 API가 리다이렉트의 첫 요청만 가로채는 경우를 고려하고, 모르는 위치로 자동 이동해 통신을 허용하지 않는다.
9. 업무 데이터 변경 요청이 한 번이라도 허용되었거나 분류가 불명확하면 테스트 실패로 기록한다. 조회 결과를 운영 전체에 대해 수집해 보관하지 않고 필요한 화면 구조와 최소 판정 결과만 사용한다.

조회·로그인도 접근 기록과 세션 상태는 만들 수 있다. 여기서 금지하는 것은 교인·교육·소속 등 운영 업무 데이터의 테스트 변경이다. 이를 ‘서버의 어떤 상태도 변하지 않는 실행’이라고 표현하지 않는다.

### 10.3 모의 페이지와 저장 경계 시험

실제 화면에서 읽은 필드 ID·역할·프레임 관계를 구조 계약으로 정리하고, 실제 명단·hidden 토큰·개인사진 없이 새 합성 HTML을 만든다. 원본 페이지나 HAR를 그대로 저장소에 복제하지 않는다. 현재 로그인 페이지 구조와 기존 검색 코드만으로 등록 화면 전체가 같다고 판단하지 않는다.

모의 페이지는 저장 요청을 운영으로 전달하지 않고 로컬 응답으로 끝낸다. 신규 저장 성공·이미 존재·유효성 오류·500·지연·저장 완료 후 응답 유실·팝업 실패·검색 결과 여러 페이지를 재현한다. mock 저장 후 재조회는 독립된 모의 서버 상태에서 읽고 입력값을 그대로 성공값으로 돌려주는 가짜 검증을 피한다.

차단기의 대조군도 모의 환경에서 만든다. 차단이 없을 때는 모의 저장 처리기에 정확히 1건 도착하고, 차단했을 때는 0건 도착해야 한다. 운영 저장 버튼을 눌러 대조군을 만드는 방식은 사용하지 않는다.

테스트 설정은 `OFFLINE_SIMULATED`, `LIVE_READONLY`, `HWP_TEST_COPY`로 구분한다. 앞의 두 모드에서 운영 writer 생성 요청은 오류로 끝나야 한다. 읽기 전용 모드의 ‘확인 후 반영’ 버튼도 활성화하지 않는다. 별도 시험 서버 writer는 확인된 시험 대상에만 연결한다.

### 10.4 주보 테스트 사본

개인정보를 제거한 기준 양식 사본에 합성 등록자·합성 인도자·누적 실적을 넣고, 번호 연속성·실적 이동·신규 인도자·교역자 제외·빨간색·표 넘침을 끝까지 시험한다. 기존 청년·타 교구 합계와 본문 영역을 보존하는지도 확인한다.

테스트 경로는 실제 주보·이번 주 기준 파일·다음 주 최종 파일과 달라야 한다. 테스트 사본에서 한글 저장→닫기→다시 열기→내용 읽기→페이지 확인까지 수행한다. 공유 저장 시험은 따로 지정한 시험 폴더에서만 진행한다. 로컬 사본 성공은 공유 서버 잠금·권한 확인을 대신하지 않는다.

### 10.5 이번 계획 작성 중 확인한 연결 근거

2026-10-26 Windows의 별도 Playwright context에서 JavaScript와 Service Worker를 끄고 실제 시작 주소를 열었다. 시작 페이지 GET은 302, `/Login/Login.aspx` GET은 200이었다. 로그인 폼의 POST 방식과 `__EVENTTARGET`·`__EVENTARGUMENT`·`__VIEWSTATE`, ID·암호 입력 요소의 존재를 확인했다. 계정 입력·로그인 제출·교인 조회·등록 폼 입력은 하지 않았다.

외부 주소를 전부 차단하는 별도 모의 context에서는 합성 화면의 저장 버튼을 실행했다. 차단 전 모의 저장 1회, 차단 후 추가 모의 저장 0회를 확인했다. 모의 페이지가 운영 주소로 향하게 만든 POST 1건·GET 1건도 request route에서 중단됐으며, 두 요청의 `requestfailed`는 `ERR_BLOCKED_BY_CLIENT` 계열이고 해당 주소의 응답은 0건이었다. 이는 이 브라우저 context의 차단 경로를 확인한 결과이며 서버 DB 전체에 대한 감사 결과나 완성된 제품의 안전성 인증은 아니다.

진단 코드는 저장소 밖 임시 경로에서 실행했다. 실제 로그인 이후 청년 검색·등록 페이지의 현재 DOM, 조회 계정의 권한, 제공자 시험 서버의 존재는 아직 확인하지 않았다. 이 한계를 해소하기 위해 운영 저장을 시도하지 않는다.

## 12. 검증·배포 규칙

### 12.1 기존 검사와 새 검사 구분

현재 Node 검사 진입점은 `npm test`다. 기존 개별 명령은 `node tests/attendance-webapp.test.js`, `node tests/education-notification.test.js`이며 전체 실행은 방문·행사 명단을 포함한 8개 파일을 찾는다.

현재 `botyard.json`의 Python 명령은 `QT_QPA_PLATFORM=offscreen settlement-automation/.venv/bin/python -B settlement-automation/tests/run_tests.py`다. 이는 POSIX 셸·Mac 가상환경 경로이며 Windows PowerShell에서 그대로 실행할 수 없다. Windows에서는 기존 `.venv/Scripts/python.exe`와 환경변수 문법으로 의미가 같은 실행을 시도하고 실제 결과를 기록한다. Qt 의존성 누락·skipped가 있으면 전체 통과로 기록하지 않는다.

이번 계획 작성 중 Windows 가상환경으로 기존 안전한 전체 실행기를 돌린 결과 74개 테스트에서 실패 4건·오류 60건이 보고됐다. 출력에 `fcntl`·`PySide6` 누락, POSIX 권한값과 Windows 권한값 차이, SQLite 임시 파일 핸들 문제를 확인했다. 기존 Python 소스는 이번 작업에서 수정하지 않았다. 이 기존 Mac 앱 검증 실패를 새 자동화의 기능 실패나 Windows 지원 근거로 사용하지 않는다. 신규 기능은 7.7절의 Windows 경계로 별도 검증한다.

기존 Mac 앱의 Windows 이식이나 해당 테스트 전체 수리는 이번 계획 작성 범위가 아니다. 구현 시작 시 저장소 필수 게이트의 플랫폼 구분을 별도 합의하고 실제 명령으로 구성해야 한다. 기존 실패를 숨기기 위해 테스트를 생략하거나 허위 통과로 바꾸지 않는다.

새 기능의 `python -B newcomer-administration/tests/run_tests.py`는 T11에서 만들 제안 명령이다. 아직 존재하지 않는 테스트를 검증 완료의 근거로 인용하지 않는다.

### 12.2 완료할 때 실행할 순서

1. 키트의 `tools/cleanup-workspace.js --completed <프로젝트 루트> --apply --auto`를 실행하고 결과를 읽는다. 미완료 계획·참조된 계획·운영 자료는 보존한다.
2. 영향받는 신규 시험의 실패→수정→통과를 확인한 뒤 기존 `npm test`와 안전한 Python 전체 검사를 실행한다.
3. SPEC·기능 사양·CHANGELOG를 바꿨으면 `node .project-check/render-spec-html.js .`로 다시 생성한다.
4. 프로젝트 루트에서 `node .project-check/project-readiness.js .`를 실행한다.
5. 키트의 `tools/check-workspace.js --project <프로젝트 루트>`를 실행한다.
6. `git diff --check`, 대상 파일 diff, 문서 링크·비밀/개인자료 포함 여부를 검토한다. 준비 검사는 경로와 문서 검사이며 실제 업무 시험을 대신하지 않는다.
7. 정해진 게이트가 모두 통과하고 다른 세션과 충돌하지 않으면 현재 저장소에 관련 변경만 커밋·push한다. 실행 환경 때문에 게이트가 미완료이면 원인과 미완료 범위를 보고하며 우회하지 않는다.

Apps Script 변경이 필요한 경우에는 `deploy-drift-check` 스킬로 운영 코드를 먼저 읽고 비교한다. 기존 운영에 의도적으로 없는 파일·함수·설정은 이유 확인 없이 추가하지 않는다. Git push는 Apps Script 배포와 다르며, 운영 배포는 별도의 명시적 승인 후 수행한다.

다음 수치는 일정 약속이 아닌 초기 추정이다. 승인된 정책·교적 등록 권한·한글 사본·지정 실행 PC가 준비됐다는 조건이다.

|---|---|---|
| 정책·원본 | T01~T03 | 2~3 작업일 |
| 교적·시트 | T04~T06 | 3~5 작업일 |

## 15. 원문·공식 기술 근거와 미검증 범위

- 원문 문서는 본문과 화면 이미지 10개를 읽었다. 화면에는 과거 연도 자료도 있으므로 현행 조직연도·군·팀·순과 한글 양식의 현재 구조를 입증하지 않는다.
- [Google Sheets batch 처리 공식 문서](https://developers.google.com/workspace/sheets/api/guides/batch)는 같은 batch 요청의 하위 변경이 함께 적용됨을 설명한다. 교적·한글·다른 파일과의 공동 취소는 이 범위에 들어가지 않는다.
- [Google Sheets batchUpdate 공식 문서](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate)는 공동 편집으로 완료 뒤 값이 달라질 수 있음을 설명한다. 원본 재조회와 담당자 편집 조정이 필요하다.
- [Playwright locator 공식 문서](https://playwright.dev/python/docs/locators)를 기준으로 현재 프레임과 의미 있는 레이블·역할에서 요소를 찾는 방식을 제안한다. 특정 디모데 selector가 현재 유효하다는 검증은 별도다.
- [한글 공식 매크로 도움말](https://help.hancom.com/hoffice/multi/ko_kr/hwp/tools/macro/scriptdefinemacro.htm)은 공식 자동화 함수 자료와 매크로 사용 경로를 안내한다. 이 자료만으로 실제 주보의 표 편집·색상·페이지 보존 가능성을 확정하지 않는다.
- [Microsoft DPAPI 공식 문서](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), [Python Windows 파일 잠금 문서](https://docs.python.org/3/library/msvcrt.html), [COM STA 공식 문서](https://learn.microsoft.com/en-us/windows/win32/com/single-threaded-apartments)를 Windows 경계 설계의 근거로 사용한다. 실제 지정 PC의 인증·파일 ACL·한글 COM 호환성은 별도 시험 대상이다.

이번 계획에서는 운영 디모데의 로그인 전 페이지를 읽기만 했다. 계정 입력·로그인 제출·교인 조회·교적 생성·Sheets 수정·공유 폴더 접근·한글 프로그램 실행·메일 발송·트리거 설치·Apps Script 배포는 수행하지 않았다. 기존 Git 이력의 운영 성공 기록을 이번 자동화의 검증 결과로 사용하지 않았다.
