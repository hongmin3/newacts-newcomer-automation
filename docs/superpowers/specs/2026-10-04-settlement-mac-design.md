# Mac 실행과 군별 정착률 관리 설계

상태: 사용자 검토용 설계. 구현·설치·운영 반영은 하지 않았다.

먼저 1절의 사용 흐름과 3절의 화면 구성을 읽는다. Mac 실행은 4절,
실패 처리와 검증은 5·6절에서 확인한다. 현재 동작의 기준은 [SPEC.md](../../../SPEC.md)다.
이 문서는 승인 후 사양에 추가할 변경안을 담으며 현재 사양을 대신하지 않는다.

## 1. 목적과 범위

군 담당자가 이번 달 출석 흐름을 확인하고, 연락이 필요한 새가족을 찾아
연락 결과와 다음 확인일을 기록할 수 있게 한다. 지금 사용 중인 Mac에서 조회와 계산을 실행한다.

1차 범위는 더블클릭으로 실행하는 Mac 앱, 월별 결과 보관, 군별 최근 4주 현황, 돌봄 기록 보존이다.
기존 누적 출석 계산과 군별 메일 수신자는 유지한다.
연속 결석 알림, 등록 시기별 비교, 새 수신자 추가는 후속 범위로 둔다.

```flow
Mac 앱 더블클릭 -> 실행 환경·인증 확인 -> 등록 명단 읽기 -> 디모데 출결 조회
디모데 출결 조회 -> 조회 품질 확인 -> 실행별 결과 보관 -> 군별 현황 갱신
군별 현황 갱신 -> 담당자의 돌봄 기록
군별 현황 갱신 -(사람이 발송 선택)-> 기존 군별 메일
조회 품질 확인 -(불충분)-> 이전 정상 현황 유지·확인 사유 표시
```

| 용어 | 뜻 |
|---|---|
| 누적 출석률 | 등록 이후 대상 주일 가운데 출석한 비율. 기존 정착률 값이다 |
| 최근 4주 출석률 | 기준일까지 지난 최근 4번의 주일 가운데 등록 이후 출석 비율 |
| 조회 완료율 | 대상자 가운데 동일인 확인과 해당 기간 출결 읽기가 끝난 사람의 비율 |
| 돌봄 기록 | 담당자가 직접 적는 연락일·진행 상태·다음 확인일 |

## 2. 확인한 현재 상태

| 근거 | 확인 내용 |
|---|---|
| `settlement-automation/main.py` | Python 실행 입구. Windows 전용 코드는 없다 |
| `settlement-automation/run_monthly.ps1` | Windows 가상환경 경로로 월말 조회·메일을 실행한다 |
| `settlement-automation/settlement_automation.py` | 출결 조회, 누적 계산, 시트 전체 갱신, 고정 파일명 CSV 저장 |
| `settlement-automation/settlement_email.py` | 마지막 화요일 판정, 전체 조회 완료율 검사, 월별 발송 기록 |
| `settlement-automation/tests/test_settlement.py` | 날짜 판정·메일 내용·완료율 검사 등 기존 테스트 5개 |
| 현재 Mac 환경 | macOS 26.6.2, arm64, Python 3.14.7. 패키지 호환성은 설치 후 검증 필요 |

현재 Mac 작업 폴더에는 `config.py`, Google 인증 파일, `.venv`, 운영 발송 상태 파일이 없다.
기존 Windows 예약 작업의 활성 상태는 이 Mac에서 확인하지 못했다.

기존 구현은 CSV와 시트의 최신 결과를 덮어쓴다. 군별 월간 변화나 수동 연락 기록을
같은 결과 영역에 추가하면 다음 갱신 때 사라질 수 있다.

현재 `최근 4주`는 개인의 등록 이후 마지막 최대 4번 주일을 계산한다.
새 군별 비교 지표는 모두 같은 기준일의 최근 4번 주일을 사용하도록 별도로 정의한다.

## 3. 군별 관리 화면과 계산

### 화면 구성

탭 이름은 새로 만들 때 사용할 제안이다. 기존 이름·열 위치는 바꾸지 않는다.
같은 이름의 탭이 이미 있으면 내용과 소유자를 확인한 뒤 연결하고 임의로 초기화하지 않는다.

| 탭 | 담당자가 보는 내용 | 기록 주체 |
|---|---|---|
| 기존 `정착률` | 기존 누적 출석률·군별 요약·개인 상세 | 기존 자동화 |
| `군별 정착 현황` | 기준일, 군, 인원, 조회 완료율, 누적·최근 4주 출석률, 전월 차이 | 자동화 |
| `정착률 월별 이력` | 군별 월별 요약, 실제 조회일, 계산 기준일, 당시 군, 산식 버전 | 자동화 |
| `새가족 돌봄 기록` | 담당자, 최근 연락일, 진행 상태, 다음 확인일, 짧은 메모 | 담당자 |

메모에는 상세 상담 내용이나 민감한 사유를 넣지 않는다. 군별 화면은 전체 현황이므로
편집 권한을 구분한다. 군별 필터만으로 열람 권한이 분리되는 것은 아니다.
담당자의 연락 기록은 자동 갱신 영역과 분리하고 자동화가 기존 입력을 덮어쓰지 않는다.

### 계산 규칙 제안

1. 누적 출석률은 조회 완료자의 출석 주일 합계를 대상 주일 합계로 나눈다.
2. 최근 4주는 기준일까지 지난 일요일 4개를 공통으로 잡는다.
3. 개인별 분모에는 그중 등록일 이후 주일만 넣는다. 군별 비율은 분자·분모 합계로 계산한다.
4. 등록 후 대상 주일이 4개 미만이면 `관찰 기간 부족`으로 표시하고 별도 인원을 보여준다.
5. 조회 실패·동일인 미확정은 출석률 계산에서 제외하고 확인 대상 인원에 넣는다.
6. 대상 주일이 0이면 `계산 대상 없음`, 분모가 없으면 비율 대신 빈 값을 표시한다.
7. 전월 값이 없거나 계산 기준이 다르면 차이를 표시하지 않는다. 차이는 퍼센트포인트로 표시한다.

전월 차이는 당시 군별 구성원 전체의 요약 비교다. 새 등록이나 군 이동에 따른 인원 차이도
함께 표시하고, 이를 같은 사람들의 출석 개선으로 해석하지 않는다.

군이 없으면 `미배정`, 지원하지 않는 군이면 `군 확인 필요`로 남긴다.
기존 군별 운영 메일에는 이들을 임의 군으로 배정하거나 새 수신자에게 보내지 않는다.

연락 대상 자동 판정은 1차 범위에서 확정하지 않는다. 담당자는 최근 4주 현황을 보고
돌봄 기록에 직접 대상을 등록한다. 저출석 표시를 정착 실패 판정으로 사용하지 않는다.

### 이력과 사람 식별

확정한 디모데 ID를 사람 연결의 기준으로 쓴다. 행 번호나 이름만으로 연락 기록을 연결하지 않는다.
ID가 없거나 여러 명과 일치하면 자동 연결을 멈추고 확인 대상으로 남긴다.
군 이동 시 동일한 사람의 연락 기록은 이어지고, 과거 결과의 군은 당시 값으로 보존한다.

실행별 CSV는 시각과 실행 번호를 포함한 새 파일로 저장한다. 개인정보 결과는 Git 밖에 둔다.
로컬 SQLite에는 실행 상태·발송 진행과 이력 위치를 저장하고 정상 결과를 다시 읽을 수 있게 한다.
백업은 교회가 승인한 비공개 저장 위치를 지정한 후 연결한다. Git과 공개 문서를 백업으로 쓰지 않는다.

월별 요약은 군·보고 월·산식 버전으로 같은 기록을 찾는다. 같은 월을 다시 조회하면
실행별 원본은 각각 보관하고, 마지막 정상 실행을 그 월의 표시값으로 선택한다.
월별 표시값은 해당 월에 사람이 실행한 정상 결과 중 가장 최근 값을 사용한다. 기준일은 기본적으로 실행 당일이다.
그 달 실행이 없으면 `미실행`으로 표시하고 앞달 값을 이번 달 값처럼 사용하지 않는다.
과거 기준일 조회는 화면에서 날짜를 선택한다. 기준일 이후 등록자는 포함하지 않는다.
늦게 입력된 명단이나 수정된 디모데 출결로 결과가 달라질 수 있어 조회 시각도 기록한다.

## 4. 더블클릭으로 실행하는 Mac 앱

### 선택한 방식과 대안

현재 Python 조회·계산을 공통으로 쓰고, Mac용 `새가족 정착률.app`을 만든다.
사용자가 Finder나 Dock에서 앱을 열면 화면이 뜨고 실행 준비 확인 후 조회를 시작한다.
터미널 명령이나 가상환경 활성화를 매번 요구하지 않는다. 예약 작업은 추가하지 않는다.

| 방식 | 장점 | 제약 | 선택 |
|---|---|---|---|
| Python·Chromium을 포함한 `.app` | 앱 실행만으로 사용, 진행·오류를 화면에 표시 | 패키지 크기가 크고 빌드 검증 필요 | 추천 |
| 기존 Python을 호출하는 `.command` | 제작이 간단 | 실행 환경 설치와 터미널 창이 필요 | 채택하지 않음 |
| 브라우저에서 여는 별도 서버 | 여러 기기에서 접근 가능 | 서버 운영과 별도 인증이 필요 | 후속 범위 |

현재 Mac의 Apple Silicon(arm64)에 맞춰 PyInstaller로 실행 묶음을 만드는 방식을 검증한다.
기존 Python 코드는 계산·조회 계층에 두고, PySide6 화면에서 별도 작업으로 실행한다.
화면 갱신이 조회 때문에 멈추지 않도록 작업과 진행 이벤트를 분리한다.
구현 시 라이브러리 호환성과 포함 파일을 실제로 검증하고 버전을 고정한다.

[PyInstaller의 Mac 앱 묶음 설명](https://pyinstaller.org/en/stable/spec-files.html#spec-file-options-for-a-macos-bundle)에 맞춰
폴더형 앱 묶음에 런타임을 포함한다. 처음 실행할 때 패키지를 내려받는 방식은 사용하지 않는다.

| 구성 요소 | 책임 | 다른 부분과 연결 |
|---|---|---|
| 앱 화면 | 설정·인증·진행 표시·취소·메일 미리보기 | 실행 작업에 요청을 보내고 진행 이벤트를 받는다 |
| 실행 작업 | 명단 읽기부터 결과 확정까지 단계 제어 | 기존 조회·계산 함수에 기준일과 설정을 전달한다 |
| 설정·경로 관리 | 앱 자원과 사용자 데이터 위치 구분 | Google 인증·결과 저장·키체인 연결에 경로를 제공한다 |
| 이력 관리 | 실행별 결과와 월별 선택값 보관 | 군별 화면과 재실행에 이전 정상 결과를 제공한다 |
| 보고서 발송 | 사용자가 선택한 보고 범위 발송 | 결과·기존 수신 범위·발송 진행 기록을 받는다 |

현재 공통 코드의 `import config`, `PROJECT_DIR`, 고정 CSV 경로는 앱 외부 사용자 설정과
데이터 위치를 주입할 수 있게 바꾼다. 기존 CLI는 같은 실행 작업을 호출하며 기존 옵션을 유지한다.
빌드에 포함된 코드 경로를 쓰기 가능한 데이터 폴더로 취급하지 않는다.

Playwright는 macOS에서 Python 브라우저 자동화를 지원한다.
[공식 지원 환경](https://playwright.dev/python/docs/intro)을 확인했다.
현재 Python 3.14에서 이 프로젝트 패키지와 Chromium 실행이 되는지는 아직 검증하지 않았다.
빌드에 사용한 Python과 Chromium을 앱 안에 포함하여 사용자가 별도로 설치하지 않게 한다.
현재 사용자의 Apple Silicon Mac을 1차 대상에 둔다. Intel Mac·Windows 실행파일은 이번 범위에 없다.

### 실행 화면과 사용 순서

1. 앱을 더블클릭한다. 기존 실행이 있으면 새 조회를 시작하지 않고 진행 중임을 안내한다.
2. 최초 실행에서는 Google 인증 파일을 선택하고 Google 승인을 완료한다.
3. 디모데 로그인은 최초 설정 화면에서 확인하고, 자동 로그인 정보는 Mac 키체인에 보관한다.
4. 준비가 끝나면 실행 당일을 기준으로 전체 조회·계산·시트 갱신을 시작한다.
5. 화면에 `명단 읽기 → 출결 조회 → 계산 → 시트 갱신` 진행 상태와 완료·확인 필요 인원을 표시한다.
6. 완료 후 `정착률 시트 열기`, `군별 현황 보기`, `메일 보고서 미리보기`를 선택할 수 있다.
7. 메일은 결과와 기존 수신 범위를 보여준 뒤 `보고서 보내기`를 눌렀을 때 발송한다.

설정된 앱은 열 때마다 새로운 전체 조회를 시작한다. 앱 실행 자체가 시트 갱신 요청이다.
메일은 앱 실행만으로 발송하지 않는다. 최초 인증이 끝나기 전에는 조회·시트 변경·메일 발송을 하지 않는다.
`1명 시험 조회`는 설정 화면에 두고 결과를 시험 전용 위치에 저장하며 시트와 메일을 바꾸지 않는다.

기본 화면에는 기준일, 진행 단계, 완료 인원, 오류 요약을 표시한다.
예상 소요 시간은 실제 측정 전에는 제시하지 않는다. 사용자에게 기술 로그를 읽게 하지 않고
인증 만료·네트워크 끊김·동일인 미확정에 맞는 다음 행동을 화면에 안내한다.

취소하면 진행 중인 사람의 조회가 끝난 안전한 시점에 멈추고 정상 현황을 갱신하지 않는다.
앱 종료·컴퓨터 종료로 중단된 실행은 다음 시작 때 감지한다. 완료한 단계와 결과를 확인한 뒤
사용자가 이어서 실행하거나 새로 시작하도록 한다. 중단된 메일은 자동 재발송하지 않는다.

### 앱과 데이터 위치

| 위치 | 담는 내용 |
|---|---|
| `/Applications/새가족 정착률.app` 또는 사용자 Applications 폴더 | 실행 프로그램·Python·Chromium·화면 |
| 사용자 `Library/Application Support`의 앱 전용 폴더 | 설정·Google 토큰·실행 이력·CSV·발송 진행 |
| 사용자 `Library/Logs`의 앱 전용 폴더 | 개인정보 없는 운영 진단 로그 |
| Mac 키체인 | 디모데 로그인 정보 |

앱 설치 위치와 결과 보관 위치를 분리한다. 앱을 새 버전으로 바꿔도 이력과 인증을 유지한다.
앱은 저장소와 현재 터미널 경로에 의존하지 않는다. 인증과 개인정보는 앱 빌드에 포함하지 않는다.
토큰·결과 파일에는 현재 사용자만 접근할 수 있게 한다.
Google·디모데 접근에는 인터넷이 필요하다. 인증이 만료되면 앱 안에서 다시 인증하도록 안내한다.

추가할 파일은 앱 화면, 실행 작업 제어, 설정·키체인 연결, 패키징 설정, Mac 빌드 도구다.
구현 후 Finder 더블클릭 경로에서 Chromium 실행과 결과 저장까지 확인한다.

### 기존 Windows 운영과 함께 사용할 때

기존 Windows 예약 작업과 이 Mac의 수동 실행이 겹치면 시트 갱신·메일이 중복될 수 있다.
Mac을 주 실행 도구로 전환할 때 기존 Windows 작업의 활성 상태와 발송 기록을 확인한다.
이번 변경은 Windows 작업을 자동으로 중지하거나 변경하지 않는다.

운영 전환 순서는 Mac 시험 조회, 기존 상태 확인·이관, 기존 Windows 자동 실행 정리,
Mac 시트 갱신과 테스트 메일 확인이다. Windows 상태를 확인하지 못하면 운영 전환을 완료로 표시하지 않는다.
Mac 프로세스 잠금은 다른 컴퓨터까지 잠그지 않으므로 운영 실행 주체를 한 대로 정한다.

## 5. 실패·재실행 처리

- 전체 조회 완료율 95% 기준을 유지한다. 군별 조회 완료율도 보여주고,
  군별 메일에도 같은 95% 기준을 적용하는 변경을 제안한다.
- 읽은 출결 연도·날짜 범위를 검증한다. 해당 화면을 못 읽은 상태를 결석으로 채우지 않는다.
- 품질 검사를 통과한 결과만 최신 정상 현황으로 선택한다. 실패 결과는 비공개 실행 이력에 보관한다.
- 새 현황은 로컬 결과를 확정한 뒤 시트에 반영한다. 부분 반영 시 단계별 진행을 기록하고
  같은 실행 번호로 완료하지 못한 단계부터 복구한다.
- 메일 발송은 실행 번호·보고 범위별로 진행을 기록한다. 일부 실패 시 확인된 성공 보고서는 다시 보내지 않는다.
  같은 결과를 다시 발송하려면 마지막 발송일을 화면에 보여주고 사용자의 재발송 선택을 받는다.
- 전송 성공 직후 기록에 실패했거나 전송 결과가 불명확하면 `발송 확인 필요`로 남긴다.
  자동 재발송하지 않는다. 메일 전송과 로컬 기록은 하나의 작업으로 묶을 수 없기 때문이다.
- 수동 시험 CSV는 운영 결과·운영 발송 상태와 별도로 저장한다.
- 등록일의 연도는 명시된 연도를 우선 사용한다. 연도가 없는 날짜는 운영 기준 연도와
  명단 기간으로 해석하고, 불명확한 연말 날짜는 확인 대상으로 남긴다.
  현재의 2025·2026 고정 해석을 다음 해에도 그대로 사용하지 않는다.

## 6. 검증과 완료 기준

| 확인할 내용 | 검증 방법 |
|---|---|
| Mac 실행 환경 | 가상환경에서 의존성 설치, 실제 Chromium 시작·종료, 경로·인증 준비 검사 |
| 계산 | 0주·1주·4주·연말 경계, 미조회, 미배정, 군 이동을 가짜 입력으로 검사 |
| 월별 이력 | 같은 달 재실행·다른 기준일·산식 변경에도 이전 실행 원본이 보존되는지 검사 |
| 앱 실행 | 첫 인증·설정 완료·인증 만료·중복 실행·취소·다시 열기를 검사 |
| 기록 보존 | 자동 갱신 전후 담당자가 쓴 돌봄 기록을 비교 |
| 장애 복구 | 조회 실패·시트 부분 반영·메일 일부 실패·발송 결과 불명확을 재현 |
| Mac 실제 경로 | 터미널 없이 Finder에서 앱을 더블클릭하고 시험 조회·진행 화면·결과 파일을 확인 |
| 운영 확인 | 승인된 범위로 시트 갱신·다시 읽기, 사용자가 선택한 테스트 메일 도착, 기존 Windows 상태 확인 |

기존 Node 검증과 Python 테스트를 유지하고, 새 계산·실행 상태 테스트를 공통 검증에 연결한다.
새 기능은 사양에 Requirement와 테스트 연결을 추가한 뒤 구현한다.
문서 검사와 가짜 입력 테스트만으로 운영 완료를 표시하지 않는다.

## 7. 구현 순서와 검토 요청

1. 앱 화면·최초 설정·더블클릭 실행·시험 결과 분리부터 구현한다.
2. 실행별 결과 보관, 최근 4주 지표, 군별 요약과 돌봄 기록 연결을 구현한다.
3. 중단 복구·단계별 복구·보고서별 발송 상태를 구현한다.
4. Python·Chromium을 포함한 앱을 빌드하고 Finder 실행과 Windows 전환 절차를 검증한다.

검토할 결정은 앱을 열면 전체 조회·시트 갱신을 시작하고 메일은 별도 선택하는 흐름, 새 탭 구성,
군별 발송에도 조회 완료율 95% 적용이다. 검토 승인 후 정식 사양과 구현 계획을 작성한다.
그때 각 새 요구사항에 프로젝트 전체에서 겹치지 않는 ID를 부여한다.

인증 승인, 기존 Windows 상태 확인, 비공개 백업 위치 지정은 운영 적용 때 필요한 확인이다.
현재는 설계만 완료했으며 앱 구현·설치·조회·시트 갱신·메일 발송을 수행하지 않았다.
