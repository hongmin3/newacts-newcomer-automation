이 문서는 뉴액츠 새가족 자동화가 어떻게 동작해야 하는가를 정의하는 기준이다. 코드가 현재 그렇게 동작한다는 사실은 사양이 아니다. 사양과 구현이 다르면 코드에 맞춰 이 문서를 고치지 말고 SPEC / CODE MISMATCH로 식별한다 — 절차는 AGENTS.md에 있다.

1. 목적

새가족부 운영진이 새가족의 등록 → 교육 출석 → 수료 → 보고를 손으로 옮겨 적지 않고 운영하기 위한 자동화다. 출석 응답이 들어오면 사람이 개입하지 않아도 교육 명단·등록 명단· 수료현황이 서로 맞고, 주간 운영 판단에 필요한 명단과 통계가 정해진 시각에 담당자에게 메일로 도착하는 것이 성공 조건이다.

자동으로 판단할 수 없는 건은 임의로 고치지 않고 검토 대상으로 보고한다. 조용히 틀린 값을 쓰는 것보다 사람이 확인하도록 남기는 쪽이 항상 옳다.

2. 프로젝트 범위

포함

  • 새가족 교육 출석 입력 웹앱(본인 확인, 주차 검증, 응답 시트 기록)
  • Google Form 출석 응답을 교육 출석 현황 시트에 증분 반영
  • 집중교육 참석 결과를 교육 출석 현황에 병합
  • 등록 명단의 군·팀·전화번호를 교육 출석 기준으로 자동 보정하고 군 현황판 갱신
  • 교육 출석과 등록 명단을 결합한 수료현황 재작성 및 주간 전체·군별 보고 메일
  • 토요일 문자공지 대상 명단(교육 진행 중 / 교육 미진행) 메일
  • 집중교육 신청 Form 접수와 관리자·공개 명단 실시간 동기화
  • 실행 결과의 숨김 로그 기록과 메일 수신자 안전장치
  • 저장소 ↔ 운영 Apps Script 동기화 도구(scripts/apps-script.mjs)

제외

  • 실제 문자(SMS) 발송. 이 자동화는 발송 대상 명단과 번호 목록까지만 만든다.
  • 정착률 계산과 월간 정착률 메일. 외부 시스템 로그인이 필요해 Apps Script 실행 기반 밖에 있다(docs/settlement-monthly-email-analysis.md).
  • 개인 명단·실행 결과 데이터의 저장소 보관. 데이터는 Google Sheets에만 둔다.
  • 교육·등록 정기 트리거의 자동 생성·변경. 이 일정은 Apps Script 화면에서 사람이 관리한다. 집중교육 신청 설치 함수의 제출 트리거 생성은 포함한다.
  • 운영 배포의 자동화. 배포는 명시적 승인 후 수동으로 실행한다.

3. 시스템 구성

네 개의 독립된 Apps Script 프로젝트로 이루어진다. 한 디렉터리 = 한 Apps Script 프로젝트이며, 같은 디렉터리의 .gs 파일은 전역 설정과 공통 함수를 공유하므로 독립 스크립트로 분리하지 않는다.

4. 전체 동작 흐름

  1. 참석자가 출석 웹앱에서 이름·전화번호로 조회하고 이번 주차 출석을 제출한다.
  2. 제출 값은 서버에서 다시 검증된 뒤 출석 응답 시트의 헤더 바로 아래(2행) 에 삽입된다.
  3. 교육 프로젝트가 화요일 17:00~18:00에 한 번 실행되어, 타임스탬프 커서 이후의 새 응답만 오래된 순으로 교육 출석 현황에 반영하고 결과를 메일과 숨김 로그로 남긴다.
  4. 등록 프로젝트가 월요일에 교육 출석을 기준으로 등록 명단의 군·팀·전화번호를 보정하고 군 현황판을 다시 쓴다. 사람이 직접 고친 값은 보호한다.
  5. 등록 프로젝트가 금요일에 등록 명단과 교육 출석을 전화번호로 결합해 수료현황을 다시 쓰고 전체 관리자와 군 담당자에게 주간 통계를 보낸다.
  6. 교육 프로젝트가 토요일에 문자공지 대상 명단과 번호 목록을 메일로 보낸다.
  7. 집중교육 신청은 위 흐름과 분리된 독립 프로젝트로, Form 제출 즉시 관리자 명단과 공개 확인 명단을 갱신한다.

5. 기능 요구사항

ID 규칙: REQ-<CATEGORY>-NNN. CATEGORY는 대문자·숫자, NNN은 세 자리. 한 번 부여한 ID는 재사용하거나 의미를 바꾸지 않는다. 삭제한 ID를 다른 기능에 돌려쓰지 않는다.

implemented구현 attendance-webapp/Code.gs테스트 TEST-ATTEND-001참조됨 TEST-ATTEND-001변경 이력 CHANGELOG에 이 ID로 기록된 변경 없음

목적

출석 웹앱이 잘못된 입력과 중복·변조된 제출을 시트에 남기지 않게 한다.

동작

  • 조회는 이름과 휴대폰 번호가 모두 일치하는 기존 응답에서 가장 높은 주차를 돌려준다.
  • 제출 값은 클라이언트 검증을 신뢰하지 않고 서버에서 다시 검증한다. 이름(30자 이하), 휴대폰 번호(10~11자리), 주차(1~4), 군(허용 목록)을 확인한다.
  • 1주차 제출은 유입 경로·성별·나이를 모두 요구한다. 2주차 이상은 기존 이력에서 성별·나이를 가져오고, 이력이 없으면 접수하지 않는다.
  • 접수 가능한 주차는 기존 최고 주차 + 1 하나뿐이다.
  • 이미 기록된 주차를 다시 제출하면 새 행을 만들지 않고 중복으로 응답한다.
  • 제출 전 구간은 스크립트 잠금으로 감싸 연속 클릭·동시 요청이 중복 행을 만들지 못하게 한다.
  • 화면에 사용자 이름을 넣을 때 HTML을 이스케이프한다.

예외 처리

검증 실패·잠금 획득 실패·이력 불일치는 모두 예외로 중단하고 시트를 바꾸지 않는다. 사용자에게는 원인을 알 수 있는 메시지를 보여 준다.

목적

운영자가 보는 응답 시트를 항상 최신순으로 유지한다.

동작

  • 신규 응답은 시트 끝이 아니라 헤더 바로 아래 2행에 삽입한다.
  • 삽입한 행의 타임스탬프 열에 시트와 동일한 날짜 형식을 적용한다.
  • 과거 응답을 한 번에 최신순으로 정렬해야 할 때는 sortAttendanceSourceNewestFirst를 1회 수동 실행한다. 정기 실행이 시트 전체를 다시 정렬하지 않는다.
  • 삽입 위치가 바뀌어도 교육 반영은 행 번호가 아닌 타임스탬프를 기준으로 하므로 누락이 생기지 않아야 한다(REQ-EDU-001).

예외 처리

삽입 실패 시 예외가 전파되고 잠금을 해제한다. 행 삽입·값 쓰기·서식 지정은 별도 호출이며, 실패 시 부분 기록의 자동 롤백은 보장하지 않는다.

9. 오류 처리 정책

  • 교육 증분 처리의 처리 범위는 저장된 커서로 정한다. 시트·커서·로그·메일은 단일 트랜잭션이 아니므로 실패 단계에 따라 다음 실행이 복구하지 못하는 작업이 있을 수 있다. 실패 시 커서와 실제 반영 상태를 확인한다. 트리거 실패 알림은 Apps Script 설정에 위임한다.
  • 부분 성공을 허용한다. 자동 판단이 가능한 행만 반영하고, 나머지는 시트를 바꾸지 않은 채 검토·중복·충돌로 분류해 메일과 숨김 로그에 남긴다. 검토 항목을 자동으로 추측해 고치지 않는다.
  • 중단해야 하는 조건은 다음과 같다. 필요한 시트·스프레드시트를 찾지 못한 경우, 잠금 획득 실패, 메일 수신자 안전장치 위반, 웹앱 입력 검증 실패, 웹앱에서 요청 주차가 이력과 맞지 않는 경우, push 후 재검증 불일치, 집중교육 설치 검증 실패(생성물 정리 시도 후 중단).
  • 아무 일도 하지 않고 정상 종료하는 조건: active가 거짓, 새 응답 0건, 처리 기준 커서가 없어 초기화가 필요한 경우.
  • 기록 위치: 실행 요약은 각 스프레드시트의 숨김 로그 시트, 상세는 결과 메일, 예외와 진행 로그는 Apps Script 실행 로그.
  • 미리보기 함수는 어떤 실패 경로에서도 시트·속성·메일을 바꾸지 않는다.

10. 보안 요구사항

  • 인증 수단은 두 가지다. Apps Script 실행 계정 권한(시트·메일·드라이브)과, 로컬 동기화 도구가 재사용하는 clasp refresh token. 토큰 파일은 사용자 홈에만 두고 저장소에서 제외한다.
  • 저장소에 들어가면 안 되는 값: 개인 명단, 실행 결과, 인증 토큰, 개인 절대경로. 스프레드시트·스크립트 식별자는 운영 코드에 필요한 범위에서만 두고 이 사양 문서에는 쓰지 않는다.
  • 출석 웹앱은 익명 접근을 허용하되, 실행 권한은 배포자 계정이며 조회에 이름과 전화번호를 모두 요구한다. 외부 iframe 임베드는 허용하지 않는다.
  • 사용자 입력을 HTML에 넣기 전 이스케이프한다.
  • 집중교육 관리자 파일은 비공개, 공개 확인 시트만 링크 뷰어다(NFR-SEC-001).
  • 운영 수신자, 시트 식별자·이름·열 위치, 트리거 함수명, active, mode는 근거 없이 바꾸지 않는다.
